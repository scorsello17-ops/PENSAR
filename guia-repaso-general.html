Bloque 1 · Estructura de datos
Datos en formato tabular — el punto de partida
Fundamentos

Como analistas de datos, la mayoría de veces trabajamos a través de tablas. Toda tabla tiene:

  • Fila → un registro individual (una compra, un cliente)
  • Columna → una característica (nombre, importe, segmento)
  • Celda → el valor concreto en la intersección

Las tablas no se explotan de forma arbitraria — siguen una estructura organizada en Facts y Dimensions. Eso hace que el análisis sea más óptimo y la estructura de los esquemas más clara.

Fact Tables vs Dimension Tables — la diferencia clave
Estructura

La diferencia principal está en con qué frecuencia se actualiza el dato:

TipoGuardaFrecuenciaEjemplo en el caso
Fact TableTransacciones, eventosAlta — puede haber +10.000 entradas al díaorder_line_table — cada venta
Dimension TableInformación de entidades (clientes, productos)Baja — un cliente no cambia sus datos constantementeclient_table — ficha de cada cliente
Alfons: "En el caso de clientes, no nos van a entrar tantos clientes nuevos de forma diaria. Un cliente no va a cambiar mucho su información personal — puede mudarse, sí, pero no pasa de forma constante."

Patrón

Como analistas, todo lo que hacemos sigue este patrón:

Pregunta en clase
¿COFFEE_PRODUCT es una métrica o una dimensión?
Es una dimensión — no se suma, se usa para agrupar o filtrar. Lo que se suma es NB_SLEEVES (las cajas vendidas). COFFEE_PRODUCT es el nombre del café → con eso filtrás o agrupás.
CLIENT_SEGMENT también es dimensión aunque sea un número (1 al 6). La clave no es si es número o texto — es si lo vas a SUMAR o a AGRUPAR.
IDs, PK, FK y tipos de relaciones entre tablas
Relaciones

Los identificadores (IDs) permiten conectar tablas entre sí. Los informáticos asignan números únicos a cada entidad para no repetir texto.

ConceptoDónde está¿Se repite?
Primary Key (PK)Dimension Table — client_tableNo — aparece 1 vez por cliente
Foreign Key (FK)Fact Table — order_line_tableSí — un cliente puede tener N pedidos

Tipos de relaciones:

  • 1:1 — un registro en cada tabla
  • 1:N — un cliente puede tener muchos pedidos (la más frecuente)
  • N:N — muchos a muchos (no se puede usar BUSCARV directamente)
Para BUSCARV funcione correctamente, necesitamos relación 1:N — el CLIENT_ID debe aparecer una sola vez en la tabla de referencia (client_table). Si hay N:N, BUSCARV no puede utilizarse de forma correcta.

El Business Case — Unicorn Espresso
Caso
  • Empresa: Unicorn Espresso — cápsulas de café premium (tipo Nespresso), 35.903 clientes.
  • Doble campaña: envío de carta física al 50% de clientes + lanzamiento de 2 ediciones limitadas (Caffè Venezia LE y Café Istanbul LE).
  • Coste campaña: €27.000. Precio por sleeve: €4,50 (sleeve = caja de 10 cápsulas).
  • Grupo tratamiento: 50% que recibió la carta. Grupo control: 50% que no recibió nada.
En un mundo ideal, no se testearían 2 cosas a la vez (carta + LE). En la realidad, todo se lanza junto. El analista trabaja con eso y es transparente sobre las limitaciones.

Bloque 4 · Cálculo de métricas
Enriquecer la tabla — el Paso 0
BUSCARV

Antes de calcular cualquier métrica, se importaron 2 columnas de client_table a order_line_table usando BUSCARV (VLOOKUP):

  • CLIENT_SEGMENT → para saber el segmento de ese cliente en cada pedido
  • RECEIVED_COMMUNICATION → para saber si recibió mailing o no

Esto creó la "tabla enriquecida" que permitía responder todas las métricas de forma más rápida y directa.

// Traer CLIENT_SEGMENT (columna 2 de client_table):
=BUSCARV(A2; client_table!A:E; 2; FALSO)

// Traer RECEIVED_COMMUNICATION (columna 5):
=BUSCARV(A2; client_table!A:E; 5; FALSO)
BUSCARV necesita relación 1:N — el CLIENT_ID debe aparecer UNA SOLA VEZ en client_table. Si la relación fuera N:N, no funcionaría correctamente.

Fórmulas

Alfons: "El 61% más de ventas al enviar la carta — y un ROI de 10,67. Ojalá siempre pasara eso. Es un caso inaudito."
Penetración de mercado — concepto y decisión
Innovación
Penetración = Sleeves LE vendidas / Total sleeves vendidas × 100

¿Qué te permite decidir la penetración?

  • Si el % es muy alto (ej: 90%) → el producto es un superéxito → mantenerlo de forma permanente en el catálogo.
  • Si el % es bajo pero esperado (ej: 5%) → edición limitada normal → repetirla en el futuro, pero no hacerla permanente.
  • Si el % es muy bajo con stock disponible → puede que no haya funcionado, o que no había stock suficiente → hay que medir el tiempo de agotamiento.
Pregunta de Mauro en clase
¿Cómo sé si el % de penetración fue bueno o malo?
Siempre se necesita un benchmark — un valor de referencia del mercado o de la propia empresa. Sin ese contexto, el número solo no dice si fue bien o mal. Lo mejor es que la empresa te dé ese valor objetivo antes del análisis.
Bloque 5 · QUERY y Dashboard
QUERY — como una pivot table pero más flexible
QUERY

QUERY hizo lo mismo que las fórmulas SUMAR.SI — pero de forma más ágil y programática. Alfons lo describió como "una pivot table pero de manera mucho más flexible".

// Ejemplo: revenue por segmento
=QUERY(1.Enriquecer!A:S;
  "SELECT E, SUM(B)
   GROUP BY E"; 1)

// Con filtro — solo segmento 1:
=QUERY(A:S;
  "SELECT E, SUM(B)
   WHERE E = 1
   GROUP BY E"; 1)
QUERY es casi idéntico a SQL. Lo que aprendiste con QUERY en Sheets te sirve directamente para SQL — las cláusulas SELECT, WHERE, GROUP BY son las mismas. Solo cambia cómo se especifica la tabla.
Dashboard BSC — diseño y herramientas
Dashboard

El Dashboard organiza visualmente los resultados de las 4 perspectivas BSC. Alfons repasó su regla de diseño:

  • "Teoría de los cuadrantes": máximo 4 cuadrantes por pantalla × máximo 4 elementos por cuadrante.
  • Los gráficos pueden ser horizontales o verticales — depende de cómo se quiera leer el dato.
  • El objetivo: que un director pueda entenderlo de un vistazo.
Alfons: "Google Sheets para el Dashboard es bastante manual. Lo que ya veréis es que la parte de Dashboards o cuadro de mandos es mucho más sencilla con Power BI."

Cheatsheet del repaso

Todo lo que Alfons repasó en la sesión, comprimido para leer en 5 minutos.

Fact Table
Registra transacciones/eventos. Crece constantemente (muchas entradas al día). Ejemplo: order_line_table. Contiene NB_SLEEVES — la métrica principal.
Dimension Table
Describe entidades (clientes, productos). Cambia poco. Ejemplo: client_table. Contiene CLIENT_SEGMENT, AVG_CONSO, AVG_BASKET_SIZE, RECEIVED_COMMUNICATION.
Granularidad
Qué representa CADA FILA. Siempre hay que preguntarlo primero. client_table: 1 fila = 1 cliente. order_line_table: 1 fila = 1 línea de pedido.
Métrica
Lo que se SUMA o PROMEDIA. Responde ¿cuánto? Ejemplo: NB_SLEEVES (número de cajas de cápsulas).
Dimensión
Lo que se usa para AGRUPAR o FILTRAR. Responde ¿por qué categoría? Ejemplo: CLIENT_SEGMENT, COFFEE_PRODUCT, RECEIVED_COMMUNICATION. Puede ser un número — lo que importa es si se suma o agrupa.
Patrón universal
[ OPERACIÓN ] sobre [ MÉTRICA ] por [ DIMENSIÓN ]. Ejemplo: SUMA de NB_SLEEVES por CLIENT_SEGMENT. Todas las fórmulas del módulo siguen este patrón.
PK (Primary Key)
ID único que NO se repite. Está en la Dimension Table. Ejemplo: CLIENT_ID en client_table — cada cliente tiene un único ID.
FK (Foreign Key)
Ese mismo ID en la Fact Table, donde SÍ se repite (un cliente puede tener muchos pedidos). CLIENT_ID en order_line_table.
Relación 1:N
1 cliente → N pedidos. La más frecuente. Necesaria para que BUSCARV funcione correctamente. Si es N:N, BUSCARV no puede utilizarse de forma correcta.
BSC
Balanced Scorecard. 4 perspectivas: Financiera (¿fue rentable?), Cliente (¿quiénes?), Procesos (¿funcionó?), Innovación (¿qué aprendemos?). Se usa para empresas establecidas evaluando una campaña.
Tabla enriquecida
order_line_table + CLIENT_SEGMENT + RECEIVED_COMMUNICATION. Paso 0 — sin ella no se pueden calcular las métricas condicionadas por segmento o por mailing.
BUSCARV / VLOOKUP
Conecta dos tablas por un ID. Necesita relación 1:N. Sintaxis: =BUSCARV(valor; tabla; nº_columna; FALSO). El índice se cuenta desde la primera columna del rango.
SUMAR.SI / SUMIF
Suma con UNA condición. =SUMAR.SI(rango_criterio; criterio; rango_suma). Rango_suma al FINAL. Ejemplo: sleeves del grupo que recibió mailing.
Lift porcentual
(Revenue_mailing − Revenue_control) / Revenue_control. Resultado del caso: +61%. El grupo con carta vendió 61% más.
ROI
(Lift€ − Coste_campaña) / Coste_campaña. Resultado del caso: 10,67. Por cada €1 en cartas, se obtuvieron €10,67 de retorno.
Penetración
Sleeves LE vendidas / Total sleeves × 100. Mide qué % del total son las ediciones limitadas. Necesita benchmark para interpretar si fue bien o mal.
Sleeve
Unidad de medida del caso. 1 sleeve = caja de 10 cápsulas. Precio: €4,50 por sleeve. NB_SLEEVES es la métrica de volumen del caso.
QUERY
Equivalente a SQL en Sheets. Cláusulas: SELECT (qué columnas), WHERE (filtrar), GROUP BY (agrupar), ORDER BY (ordenar), LABEL (renombrar). Todo en inglés. Trabaja sobre 1 tabla a la vez.
Dashboard BSC
4 cuadrantes (uno por perspectiva BSC). Máximo 4 elementos por cuadrante. El director debe entenderlo de un vistazo. En Sheets es manual — Power BI es mejor para dashboards formales.
3 variables del cliente
Consumo promedio (AVG_CONSO), Basket promedio (AVG_BASKET_SIZE) y Frecuencia de compra. Las 3 juntas permiten definir el perfil del cliente de forma completa.

Bloque 1
¿COFFEE_PRODUCT es una métrica o una dimensión? ¿Por qué?
Métricas vs Dimensiones
Es una dimensión. No se suma — se usa para agrupar o filtrar (¿cuántas sleeves vendí de Venezia LE?). Lo que se suma es NB_SLEEVES.
Bloque 1
¿Por qué BUSCARV necesita una relación 1:N para funcionar bien?
BUSCARV · Relaciones
Porque BUSCARV trae solo la primera coincidencia. Si el ID aparece varias veces en la tabla de referencia (N:N), solo trae el primer resultado — lo cual es incorrecto. Necesita que el ID aparezca una sola vez (1 lado de la relación 1:N).

Perspectiva Cliente · BSC
1. AVG_CONSO — consumo promedio mensual (cuántas cápsulas al mes).
2. AVG_BASKET_SIZE — tamaño promedio de cesta (cuántos productos por visita).
3. Frecuencia — cada cuánto va a la tienda.

Perspectiva Financiera

El 61% significa que por haber enviado la carta, se vendió un 61% más que el grupo sin carta.

Bloque 4
¿En qué se parece QUERY a SQL? ¿Cuál es la única diferencia real?
QUERY vs SQL
Son casi iguales: mismas cláusulas (SELECT, WHERE, GROUP BY, ORDER BY). La diferencia: en SQL la tabla se especifica en FROM dentro de la consulta; en QUERY va como argumento externo. SQL también puede hacer JOIN entre varias tablas; QUERY solo trabaja con una.
